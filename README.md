# Django Notifications — тестовое задание

Небольшой Django-проект, реализующий административную панель для работы с записями `Item` и систему уведомлений в реальном времени через WebSocket.

Проект сделан как решение тестового задания на Python/Django

## Что умеет проект

В административной панели Django можно:

* просматривать записи `Item`;
* создавать, изменять и удалять записи в соответствии с правами пользователя;
* видеть только свои записи обычным пользователям;
* суперпользователю видеть все записи;
* фильтровать записи по владельцу;
* фильтровать записи по полю `name`;
* использовать отдельные текстовые фильтры по `username` и `name`;
* получать уведомления об изменениях записей без перезагрузки страницы;
* получать отдельное уведомление при смене владельца записи;
* автоматически скрывать уведомления через несколько секунд;
* экспортировать текущие данные `Item` в CSV, если у пользователя есть соответствующее право.

WebSocket используется именно для доставки уведомлений в реальном времени. Redis выступает в качестве channel layer между Django/Channels и WebSocket-соединениями.

## Стек проекта

Основные технологии:

* **Python 3.13**
* **Django 5.2**
* **Django Channels 4.3**
* **Daphne** — ASGI-сервер
* **channels-redis 4.2.x** — Redis channel layer для Channels
* **Redis 7**
* **PostgreSQL 17**
* **Docker / Docker Compose**
* обычный JavaScript для клиентской части WebSocket
* HTML/CSS Django Admin

Для проекта намеренно не использовался отдельный frontend-фреймворк. Задача небольшая, а Django Admin уже предоставляет большую часть необходимого интерфейса. Поэтому добавлять React/Vue и отдельную сборку frontend здесь было бы лишним усложнением.

# Запуск проекта

## Вариант 1 — Docker Compose

Это основной и наиболее удобный способ запуска.

Перед запуском необходимо установить:

* Docker;
* Docker Compose.

После этого из корневой директории проекта выполнить:

```bash
docker compose up --build
```

После запуска приложение будет доступно по адресу:

```text
http://localhost:8000/admin/
```

При первом запуске контейнер приложения:

1. ожидает готовности PostgreSQL;
2. применяет миграции;
3. собирает static-файлы;
4. запускает команду заполнения тестовыми данными;
5. запускает Django через ASGI;
6. подключается к Redis для работы WebSocket.

Если контейнеры уже были собраны, можно использовать:

```bash
docker compose up
```

Остановить проект:

```bash
docker compose down
```

Если нужно полностью удалить контейнеры вместе с volume PostgreSQL и начать с чистой базы:

```bash
docker compose down -v
```

После этого:

```bash
docker compose up --build
```

# Тестовые пользователи

При запуске Docker-окружения автоматически создаются тестовые пользователи.

## Суперпользователь

```text
Username: admin
Password: password
```

У него есть полный доступ к Django Admin и всем объектам `Item`.

## Пользователь Ivan

```text
Username: ivan
Password: ivanivan
```

Пользователь имеет:

* `staff`-статус;
* права на `Item`;
* право на экспорт CSV.

## Пользователь Petr

```text
Username: petr
Password: petrpetr
```

Пользователь имеет:

* `staff`-статус;
* все права на `Item`, кроме экспорта CSV.

Сразу после запуска можно проверить оба варианта поведения CSV-кнопки:

* войти как `ivan` — кнопка `Скачать CSV` доступна;
* войти как `petr` — кнопка отсутствует, а прямой вызов export endpoint запрещён;
* войти как `admin` — доступен полный набор возможностей.

Тестовые пользователи и записи создаются через management command `seed_data`, поэтому данные не зависят от конкретного состояния Docker-образа.

# Как проверить WebSocket-уведомления

После запуска нужно открыть административную панель в браузере.

Например, можно открыть страницу списка `Item` под пользователем `ivan`.

Затем в другой вкладке войти как пользователь, имеющий возможность изменять записи, и изменить одну из записей.

При обычном изменении записи владелец получает уведомление.

При смене владельца предусмотрены два разных уведомления:

* старому владельцу сообщается, что запись больше ему не принадлежит;
* новому владельцу сообщается, что запись была назначена ему.

Уведомление отображается непосредственно в интерфейсе Django Admin и автоматически исчезает через несколько секунд.

# Архитектура проекта

Проект построен вокруг стандартной Django-структуры. Здесь нет необходимости разделять проект на большое количество Django-приложений.

Основная бизнес-сущность тестового задания — `Item`, поэтому связанные с ней компоненты находятся внутри приложения `items`:
* `models.py` — модель;
* `admin.py` — Django Admin;
* `filters.py` — фильтры административной панели;
* `signals.py` — реакция на изменение `Item`;
* `consumers.py` — WebSocket;
* `routing.py` — WebSocket-маршрутизация;
* `templates/` — переопределение нужных частей Django Admin;
* `static/` — JavaScript и CSS для уведомлений;
* `management/commands/seed_data.py` — подготовка демонстрационных данных.
---

# Разграничение доступа

Одна из важных частей задания — разные пользователи должны видеть разные записи.

Логика реализована непосредственно в `ItemAdmin.get_queryset()`.

Суперпользователь получает весь queryset.

Обычный staff-пользователь получает только свои записи

Дополнительно поле `owner` становится readonly для обычного пользователя.

# CSV-экспорт

CSV генерируется непосредственно Django через стандартный модуль Python:

```python
csv
```

При нажатии на кнопку формируется HTTP-ответ с заголовком attachment.

В файл попадают текущие данные `Item`, доступные конкретному пользователю.

# Уведомления об изменении Item

Для отслеживания изменений используется Django signal.

При изменении `Item` определяется:

* какая запись была изменена;
* кто был её владельцем до изменения;
* кто является владельцем после изменения;
* изменился ли владелец;
* кому необходимо отправить уведомление.

Если владелец не изменился, уведомление отправляется текущему владельцу.

# Seed-данные

Для демонстрационного окружения используется Django management command:

```text
python manage.py seed_data
```

Она создаёт:

* суперпользователя;
* двух staff-пользователей;
* необходимые permissions;
* демонстрационные `Item`.

# Принятые решения

Несмотря на то, что это тестовое задание, в реализации старались не использовать решения, которые работают только в одном конкретном сценарии.
К примеру:
* секретные настройки не должны быть жёстко зашиты в код приложения;
* база данных вынесена в отдельный контейнер;
* Redis вынесен в отдельный контейнер;
* WebSocket работает через ASGI;
* доступ к CSV проверяется на сервере;
* доступ к `Item` ограничивается на уровне queryset;
* seed-данные создаются management command;
* static-файлы собираются отдельно;
* WebSocket не зависит непосредственно от страницы конкретного Admin view.
