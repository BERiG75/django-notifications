# Django Notifications — тестовое задание

Небольшой Django-проект, реализующий административную панель для работы с записями `Item` и систему уведомлений в реальном времени через WebSocket.

Проект сделан как решение тестового задания на Python/Django с упором на понятную архитектуру, разграничение прав доступа и возможность быстро поднять полностью готовое окружение через Docker Compose.

## Что умеет проект

В административной панели Django можно:

* просматривать записи `Item`;
* создавать, изменять и удалять записи в соответствии с правами пользователя;
* видеть только свои записи обычным пользователям;
* суперпользователю видеть все записи;
* фильтровать записи по владельцу;
* фильтровать записи по полю `name`;
* использовать отдельные текстовые фильтры по `username` и `name`;
* получать уведомления об изменениях записей без перезагрузки страницы;
* получать отдельное уведомление при смене владельца записи;
* автоматически скрывать уведомления через несколько секунд;
* экспортировать текущие данные `Item` в CSV, если у пользователя есть соответствующее право.

WebSocket используется именно для доставки уведомлений в реальном времени. Redis выступает в качестве channel layer между Django/Channels и WebSocket-соединениями.

## Стек проекта

Основные технологии:

* **Python 3.13**
* **Django 5.2**
* **Django Channels 4.3**
* **Daphne** — ASGI-сервер
* **channels-redis 4.2.x** — Redis channel layer для Channels
* **Redis 7**
* **PostgreSQL 17**
* **Docker / Docker Compose**
* обычный JavaScript для клиентской части WebSocket
* HTML/CSS Django Admin

Для проекта намеренно не использовался отдельный frontend-фреймворк. Задача небольшая, а Django Admin уже предоставляет большую часть необходимого интерфейса. Поэтому добавлять React/Vue и отдельную сборку frontend здесь было бы лишним усложнением.

# Запуск проекта

## Вариант 1 — Docker Compose

Это основной и наиболее удобный способ запуска.

Перед запуском необходимо установить:

* Docker;
* Docker Compose.

После этого из корневой директории проекта выполнить:

```bash
docker compose up --build
```

После запуска приложение будет доступно по адресу:

```text
http://localhost:8000/admin/
```

При первом запуске контейнер приложения:

1. ожидает готовности PostgreSQL;
2. применяет миграции;
3. собирает static-файлы;
4. запускает команду заполнения тестовыми данными;
5. запускает Django через ASGI;
6. подключается к Redis для работы WebSocket.

Если контейнеры уже были собраны, можно использовать:

```bash
docker compose up
```

Остановить проект:

```bash
docker compose down
```

Если нужно полностью удалить контейнеры вместе с volume PostgreSQL и начать с чистой базы:

```bash
docker compose down -v
```

После этого:

```bash
docker compose up --build
```

Это особенно удобно для проверки seed-данных с нуля.

# Тестовые пользователи

При запуске Docker-окружения автоматически создаются тестовые пользователи.

## Суперпользователь

```text
Username: admin
Password: password
```

У него есть полный доступ к Django Admin и всем объектам `Item`.

## Пользователь Ivan

```text
Username: ivan
Password: ivanivan
```

Пользователь имеет:

* `staff`-статус;
* права на `Item`;
* право на экспорт CSV.

## Пользователь Petr

```text
Username: petr
Password: petrpetr
```

Пользователь имеет:

* `staff`-статус;
* все права на `Item`, кроме экспорта CSV.

Таким образом, сразу после запуска можно проверить оба варианта поведения CSV-кнопки:

* войти как `ivan` — кнопка `Скачать CSV` доступна;
* войти как `petr` — кнопка отсутствует, а прямой вызов export endpoint запрещён;
* войти как `admin` — доступен полный набор возможностей.

Тестовые пользователи и записи создаются через management command `seed_data`, поэтому данные не зависят от конкретного состояния Docker-образа.

# Как проверить WebSocket-уведомления

После запуска нужно открыть административную панель в браузере.

Например, можно открыть страницу списка `Item` под пользователем `ivan`.

Затем в другой вкладке войти как пользователь, имеющий возможность изменять записи, и изменить одну из записей.

Изменение будет отправлено через:

```text
WebSocket
    ↓
Django Channels
    ↓
Redis Channel Layer
    ↓
WebSocket-соединение пользователя
    ↓
JavaScript в Django Admin
    ↓
уведомление в интерфейсе
```

При обычном изменении записи владелец получает уведомление.

При смене владельца предусмотрены два разных уведомления:

* старому владельцу сообщается, что запись больше ему не принадлежит;
* новому владельцу сообщается, что запись была назначена ему.

Уведомление отображается непосредственно в интерфейсе Django Admin и автоматически исчезает через несколько секунд.

## Почему именно такая структура

Здесь нет необходимости разделять проект на большое количество Django-приложений.

Основная бизнес-сущность тестового задания — `Item`, поэтому связанные с ней компоненты находятся внутри приложения `items`:

* `models.py` — модель;
* `admin.py` — Django Admin;
* `filters.py` — фильтры административной панели;
* `signals.py` — реакция на изменение `Item`;
* `consumers.py` — WebSocket;
* `routing.py` — WebSocket-маршрутизация;
* `templates/` — переопределение нужных частей Django Admin;
* `static/` — JavaScript и CSS для уведомлений;
* `management/commands/seed_data.py` — подготовка демонстрационных данных.

Это позволяет не смешивать ответственность компонентов и при этом не создавать избыточную архитектуру для небольшой задачи.

# Почему используется Django Admin

В задании прямо требуется отображение `items` в административной панели Django.

Поэтому использование стандартного Django Admin позволяет получить большую часть необходимого функционала практически из коробки:

* таблицу записей;
* пагинацию;
* CRUD;
* систему permissions;
* авторизацию;
* фильтрацию;
* формы;
* работу со стандартной моделью пользователей.

При этом мы расширяем Admin только там, где это необходимо для задания.

Например, стандартного `list_filter` недостаточно для требуемых текстовых полей `username` и `name`, поэтому для них реализованы собственные фильтры.

А CSV экспорт реализован отдельным URL внутри `ModelAdmin`.

Такой подход сохраняет преимущества Django Admin и не требует писать отдельную административную панель с нуля.

# Разграничение доступа

Одна из важных частей задания — разные пользователи должны видеть разные записи.

Логика реализована непосредственно в `ItemAdmin.get_queryset()`.

Суперпользователь получает весь queryset.

Обычный staff-пользователь получает только записи, у которых:

```text
owner == request.user
```

Дополнительно поле `owner` становится readonly для обычного пользователя.

Это важно не только с точки зрения интерфейса. Ограничение применяется на уровне queryset, поэтому пользователь не просто не видит чужие записи в таблице — они не попадают в его набор данных Admin.

# Права на CSV

Для экспорта создано отдельное Django permission:

```text
export_items_csv
```

Его отображаемое название:

```text
Can export items to CSV
```

Это позволяет независимо управлять правом на экспорт.

Например, один пользователь может иметь:

```text
add_item
change_item
delete_item
view_item
export_items_csv
```

а другой:

```text
add_item
change_item
delete_item
view_item
```

При этом проверка выполняется не только при отображении кнопки.

Endpoint экспорта также самостоятельно проверяет permission.

Это важно, потому что скрытие кнопки в HTML само по себе не является защитой. Пользователь потенциально мог бы вручную открыть URL экспорта.

Поэтому реализованы два уровня:

```text
UI
 ↓
есть permission?
 ↓
показываем кнопку
```

и отдельно:

```text
HTTP request
 ↓
есть permission?
 ↓
да → CSV
нет → 403
```

# CSV-экспорт

CSV генерируется непосредственно Django через стандартный модуль Python:

```python
csv
```

При нажатии на кнопку формируется HTTP-ответ с заголовком attachment.

В результате браузер предлагает скачать файл:

```text
items.csv
```

В файл попадают текущие данные `Item`, доступные конкретному пользователю.

Это особенно важно с учётом ограничения видимости записей: обычный пользователь не должен получить через экспорт чужие записи.

Поэтому CSV строится на том же queryset, который используется Django Admin для текущего пользователя.

# WebSocket и Redis

Для уведомлений выбран Django Channels.

Обычный HTTP-запрос работает по схеме:

```text
Browser → Django → Response
```

Но уведомление об изменении записи требует обратного сценария:

```text
Django → Browser
```

без необходимости обновлять страницу.

Для этого используется WebSocket.

WebSocket позволяет держать постоянное соединение между браузером и сервером.

Но в проекте есть ещё один компонент — Redis.

Он используется как channel layer для Channels.

Получается следующая архитектура:

```text
                ┌───────────────┐
                │    Django     │
                │   + Channels  │
                └───────┬───────┘
                        │
                        ▼
                ┌───────────────┐
                │     Redis     │
                │ Channel Layer │
                └───────┬───────┘
                        │
                        ▼
                ┌───────────────┐
                │   WebSocket   │
                │    Browser    │
                └───────────────┘
```

Redis выбран не как база данных приложения, а именно как инфраструктурный компонент для обмена сообщениями между ASGI-процессами.

# Уведомления об изменении Item

Для отслеживания изменений используется Django signal.

При изменении `Item` определяется:

* какая запись была изменена;
* кто был её владельцем до изменения;
* кто является владельцем после изменения;
* изменился ли владелец;
* кому необходимо отправить уведомление.

Если владелец не изменился, уведомление отправляется текущему владельцу.

Если владелец изменился, отправляются два разных сообщения:

```text
старый владелец
    ↓
"Запись больше вам не принадлежит"

новый владелец
    ↓
"Вам назначена новая запись"
```

Такой подход позволяет не связывать логику уведомлений непосредственно с Django Admin.

Например, если `Item` будет изменён не через Admin, а другим кодом приложения, сигнал всё равно сможет обработать изменение.

# Почему не используется Celery

Для этой задачи Celery был бы избыточным.

Уведомление должно отправляться практически сразу после изменения записи, а отдельная очередь фоновых задач здесь не требуется.

Channels + Redis уже предоставляют необходимый механизм доставки сообщения.

Добавление Celery означало бы ещё один инфраструктурный компонент:

```text
Django
Redis
Celery
Worker
Channels
```

при том что для требований тестового задания это не даёт существенных преимуществ.

Поэтому используется более простой вариант:

```text
Django → Channels → Redis → WebSocket
```

# Почему PostgreSQL

В качестве основной базы данных выбран PostgreSQL.

Причины достаточно практичные:

* полноценная реляционная СУБД;
* хорошая интеграция с Django;
* удобная работа с ForeignKey;
* полноценная поддержка транзакций;
* стандартный production-oriented выбор для Django-приложений;
* легко запускается в Docker.

SQLite для такой задачи тоже технически подошёл бы, но PostgreSQL лучше соответствует окружению, которое предполагается для реального приложения.

---

# Почему Docker Compose

В проекте одновременно нужны:

* Django;
* PostgreSQL;
* Redis.

Без Docker разработчику пришлось бы самостоятельно устанавливать и настраивать PostgreSQL и Redis.

С Docker Compose всё окружение описано декларативно:

```text
web
 ↓
Django / Daphne

db
 ↓
PostgreSQL

redis
 ↓
Redis
```

Достаточно одной команды:

```bash
docker compose up --build
```

и все сервисы запускаются вместе.

Кроме того, Docker Compose позволяет явно описать зависимости сервисов и healthcheck для PostgreSQL и Redis, чтобы приложение не пыталось подключиться к ещё не готовой инфраструктуре.

# Seed-данные

Для демонстрационного окружения используется Django management command:

```text
python manage.py seed_data
```

Она создаёт:

* суперпользователя;
* двух staff-пользователей;
* необходимые permissions;
* демонстрационные `Item`.

Команда сделана идемпотентной: повторный запуск не должен создавать бесконечное количество одинаковых пользователей и записей.

Это удобнее, чем хранить тестовую базу непосредственно в репозитории или вручную создавать пользователей через Django Admin.

# Production-подход

Хотя это тестовое задание, в реализации старались не использовать решения, которые работают только в одном конкретном сценарии.

В частности:

* секретные настройки не должны быть жёстко зашиты в код приложения;
* база данных вынесена в отдельный контейнер;
* Redis вынесен в отдельный контейнер;
* WebSocket работает через ASGI;
* доступ к CSV проверяется на сервере;
* доступ к `Item` ограничивается на уровне queryset;
* seed-данные создаются management command;
* static-файлы собираются отдельно;
* WebSocket не зависит непосредственно от страницы конкретного Admin view.

При этом проект не пытается изображать полноценный production deployment с Kubernetes, Nginx, CI/CD и несколькими worker-процессами — для тестового задания это было бы неоправданным усложнением.

# Основные сценарии для проверки

После запуска можно последовательно проверить следующие сценарии.

### 1. Доступ к данным

Войти как `ivan`.

В списке должны отображаться только принадлежащие ему `Item`.

Затем войти как `petr` — должны отображаться только его записи.

`admin` должен видеть все записи.

### 2. Permissions

У `ivan` должна отображаться кнопка:

```text
Скачать CSV
```

У `petr` кнопки быть не должно.

У `admin` кнопка также доступна.

### 3. CSV

Нажать:

```text
Скачать CSV
```

Должен загрузиться файл:

```text
items.csv
```

с данными в отдельных CSV-колонках.

### 4. WebSocket

Открыть Admin под пользователем, которому принадлежит `Item`.

В другом окне изменить эту запись.

В первом окне должно появиться уведомление без перезагрузки страницы.

### 5. Смена владельца

Изменить владельца `Item` с `ivan` на `petr`.

У `ivan` должно появиться уведомление о том, что запись больше ему не принадлежит.

У `petr` должно появиться уведомление о назначении записи.

### 6. Автоматическое исчезновение

После появления уведомления подождать несколько секунд.

Уведомление должно автоматически исчезнуть.
